# 发布契约（Release Contract）

本文件是本仓库的**强制约定**。任何提交、分支操作与发布行为都必须遵守，
CI 会按此校验并在不符合时失败。

## 1. 三分支结构

| 分支 | 用途 | 版本后缀 | 产物 |
|---|---|---|---|
| `alpha` | 日常开发，改动先落这里 | `-alpha` | 开发版安装包 |
| `beta` | 已验证的功能，等待测试反馈 | `-beta` | 测试版安装包 |
| `main` | 稳定版，对外发布 | `-least` | 公测版安装包 |

**只允许存在这三个长期分支。** 其它分支（功能分支、修复分支）用完即删，
不得留在远端。

## 2. 合并方向

```
alpha ──(验证 + 我同意)──► beta ──(稳定测试 + 我同意)──► main
```

- **单向**：只允许 alpha → beta → main。
- **不可跳过**：alpha 不得直接合并到 main。
- **需要同意**：alpha → beta 和 beta → main 都必须由仓库所有者明确同意后才执行。
- **回合并禁止**：main 的改动不回流到 beta/alpha；如需修复，从 alpha 重新走一遍。

## 3. 版本号

版本唯一来源是仓库根的 `version.json`。

| 规则 | 说明 |
|---|---|
| 默认递增 | **patch**（第三位），例如 `0.0.2-alpha` → `0.0.3-alpha` |
| minor / major | **只在仓库所有者明确要求时**递增 |
| 后缀 | 跟随分支自动决定：alpha → `-alpha`，beta → `-beta`，main → `-least` |
| 前缀 `v` | tag 形如 `v0.0.3-beta` |

分支切换时后缀随之改变，数字部分保持不变。例如 beta 上的 `0.0.3-beta`
合并到 main 后发布为 `0.0.3-least`。

## 4. CI 触发

| 事件 | 行为 |
|---|---|
| push 到 `alpha` | **唯一的自动构建**：递增 patch，构建三端，发布 `vX.Y.Z-alpha` |
| push 到 `beta` / `main` | **不自动构建** |
| 手动触发（workflow_dispatch） | 由仓库所有者发起，指定分支与版本 |
| push tag `v*` | 用 tag 里的版本号发布，不再递增 |

**beta 与 main 的发布只能由仓库所有者主动发起。** 日常开发一律只产出
`-alpha`；需要 `-beta` 或 `-least` 时，由所有者明确指示后执行手动触发
或推 tag，CI 才会构建并发布对应后缀的版本。

每次发布后 CI 把递增后的 `version.json` 提交回对应分支。

## 5. 预发布与更新通道

三个后缀都是预发布标识，因此：

- 应用内更新**接受预发布版本**（`allowPrerelease`）。
- 每个通道只看自己后缀的版本，不会从 alpha 跳到 least。
- `latest` 指向最近一次成功发布。

## 6. 检查项

CI 在构建前校验：

1. 分支必须是 `alpha` / `beta` / `main` 之一，或是一次 tag 发布。
2. `version.json` 的后缀必须与分支匹配（tag 发布则与 tag 匹配）。
3. 目标 tag 不存在（避免覆盖已发布版本）。

违反任一项即失败，不会产出安装包。
