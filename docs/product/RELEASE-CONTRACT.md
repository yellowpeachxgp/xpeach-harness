# 发布契约（Release Contract）

本文件是本仓库的**强制约定**。任何提交、分支操作与发布行为都必须遵守，
CI 会按此校验并在不符合时失败。

## 1. 三分支结构

| 分支 | 用途 | 版本后缀 | 产物 |
|---|---|---|---|
| `alpha` | 日常开发，改动先落这里 | `-alpha` | 开发版安装包 |
| `beta` | 已验证的功能，等待测试反馈 | `-beta` | 测试版安装包 |
| `main` | 稳定版，对外发布 | `-least` | 公测版安装包 |

**只允许存在这三个长期分支。** 其它分支（功能分支、修复分支）用完即删，
不得留在远端。

## 2. 合并方向

```
alpha ──(验证 + 我同意)──► beta ──(稳定测试 + 我同意)──► main
```

- **单向**：只允许 alpha → beta → main。
- **不可跳过**：alpha 不得直接合并到 main。
- **需要同意**：alpha → beta 和 beta → main 都必须由仓库所有者明确同意后才执行。
- **回合并禁止**：main 的改动不回流到 beta/alpha；如需修复，从 alpha 重新走一遍。

## 3. 版本号

版本唯一来源是仓库根的 `version.json`。

| 规则 | 说明 |
|---|---|
| 默认递增 | **patch**（第三位），例如 `0.0.2-alpha` → `0.0.3-alpha` |
| minor / major | **只在仓库所有者明确要求时**递增 |
| 后缀 | 跟随分支自动决定：alpha → `-alpha`，beta → `-beta`，main → `-least` |
| 前缀 `v` | tag 形如 `v0.0.3-beta` |

分支切换时后缀随之改变，数字部分保持不变。例如 beta 上的 `0.0.3-beta`
合并到 main 后发布为 `0.0.3-least`。

## 4. CI 触发

| 事件 | 行为 |
|---|---|
| push 到 `alpha` / `beta` | 自动构建三端并发布对应通道版本（若 `version.json` 已预置为未发布的新版本与对应分支后缀则直接使用，否则自动递增 patch） |
| push 到 `main` | **不自动构建** |
| 手动触发（workflow_dispatch） | 由仓库所有者发起，指定分支与版本 |
| push tag `v*` | 用 tag 里的版本号发布，不再递增 |

**beta 与 main 的晋升合入只能由仓库所有者主动发起。** 日常开发在 `alpha` 分支产出 `-alpha`；当验证通过合入 `beta`、或由所有者明确指示执行手动触发 / 推 tag 时，CI 构建并发布 `-beta` 或 `-least` 版本。

每次发布后 CI 把递增后的 `version.json` 提交回对应分支（若推送前已在 `version.json` 中更新到目标版本号则跳过重复提交）。

## 5. 预发布与更新通道

更新通道按稳定性分为三级（`least > beta > alpha`），采用**向下兼容**（高稳定性版本向下覆盖低稳定性通道）机制：

- **`least`（正式版）**：仅接收 `-least` 正式版更新，不接收 `-beta` 或 `-alpha` 更新；
- **`beta`（测试版）**：接收 `-beta` 更新，并向下兼容接收 `-least` 正式版更新，不接收 `-alpha` 更新；
- **`alpha`（内测版）**：接收 `-alpha`、`-beta` 与 `-least` 全部更新。
- **同版本号跨通道晋升**：当同一数字版本号（如 `0.0.24`）从 `-alpha` 晋升至 `-beta` 或 `-least` 时，稳定性权重 `least > beta > alpha`，低通道客户端可平滑升级至同版本号的更高稳定性版本。
- **构建产物元数据映射**：
  - 发布 `-least` 时，同步生成 `least*.yml`、`beta*.yml`、`alpha*.yml` 与 `latest*.yml`；
  - 发布 `-beta` 时，同步生成 `beta*.yml` 与 `alpha*.yml`；
  - 发布 `-alpha` 时，生成 `alpha*.yml`。

## 6. 检查项

CI 在构建前校验：

1. 分支必须是 `alpha` / `beta` / `main` 之一，或是一次 tag 发布。
2. `version.json` 的后缀必须与分支匹配（tag 发布则与 tag 匹配）。
3. 目标 tag 不存在（避免覆盖已发布版本）。

违反任一项即失败，不会产出安装包。
